# SORA Deployment Guide (Vercel + Render + Brevo, free tiers)

*Last updated 2026-10-26 (P-18: DEP-01, DEP-02, FE-23).*

The browser only ever talks to the **Vercel** domain. Vercel serves the Next.js PWA and rewrites `/api/v1/*`
to the Django API on **Render**, so the refresh cookie is first-party on the Vercel domain (FE-23).

```
 phone / browser ──HTTPS──▶ Vercel  (Next.js PWA: sora-…vercel.app)
                              │  next.config.ts rewrites /api/v1/* → https://sora-api.onrender.com/api/v1/*/
                              ▼
                            Render web service "sora-api"  (Docker, free)
                              │   gunicorn + Celery worker with embedded beat (backend/deploy/start.sh)
                              ├──▶ Render Postgres "sora-db"       (free, expires 30 days after creation)
                              ├──▶ Render Key Value "sora-redis"   (free, Celery broker + throttle cache)
                              └──▶ Brevo HTTPS API (email) · Google Gemini API (AI)
```

| Piece | File |
|---|---|
| Render Blueprint (API, Postgres, Key Value) | `render.yaml` |
| API image | `backend/Dockerfile`, `backend/.dockerignore` |
| API start: migrate, collectstatic, worker + beat, gunicorn | `backend/deploy/start.sh` |
| Same-origin proxy | `frontend/next.config.ts` (`rewrites`, `skipTrailingSlashRedirect`) |
| Vercel upload exclusions | `frontend/.vercelignore` |
| Settings | `config.settings.prod` (the deployment); `config.settings.demo` (prod + two flags, §6) |

## Free-tier trade-offs (say these out loud in the demo)
- **Cold starts.** Render's free web service sleeps after 15 minutes without traffic. The next request
  wakes it in about a minute. **Open the app a few minutes before presenting.**
- **Reminders only run while awake.** Celery beat lives in the API container, so due-soon/overdue checks
  pause while it sleeps and catch up on the next wake-up.
- **Uploaded PDFs are temporary.** The free instance has no persistent disk. A PDF is processed right after
  upload; its summary is stored in Postgres. If the container restarts before processing finishes, the
  document is marked failed (safe message) and the user re-uploads it.
- **Email over HTTPS.** Render's free tier blocks outbound SMTP (25/465/587), so production sends through
  Brevo's API (`django-anymail`). Local development keeps its own email setup.
- **Postgres expires 30 days after creation** (then a 14-day grace period). Recreate it, or upgrade, after
  the assessment.
- **One container for API + worker + beat.** About 290 MB at idle (measured locally), inside the 512 MB
  limit with `WEB_CONCURRENCY=2` and `CELERY_CONCURRENCY=1`.

## 1. Environment variables

**Never commit values.** Secrets are typed into the Render / Vercel dashboards (or CLI) only.

### Render: `sora-api` (from `render.yaml`)
| Variable | Value |
|---|---|
| `DJANGO_SETTINGS_MODULE` | `config.settings.prod` (set by the Blueprint) |
| `SECRET_KEY` | generated by Render (`generateValue`) |
| `DATABASE_URL`, `REDIS_URL` | wired by the Blueprint to `sora-db` / `sora-redis` |
| `ALLOWED_HOSTS` | `localhost` (the Render hostname is added from `RENDER_EXTERNAL_HOSTNAME`) |
| `FRONTEND_URL` | `https://<your Vercel production domain>` (email links are built only from this) |
| `NUM_PROXIES` | measured after deploy, see §4 |
| `BREVO_API_KEY` | Brevo → SMTP & API → API keys |
| `DEFAULT_FROM_EMAIL` | `SORA <the sender address you verified in Brevo>` |
| `GOOGLE_CLIENT_ID` | the OAuth web client ID |
| `AI_PROVIDER` / `AI_API_KEY` | `gemini` (set by the Blueprint) / Gemini API key |
| `VAPID_PUBLIC_KEY` / `VAPID_PRIVATE_KEY` / `VAPID_CLAIM_EMAIL` | §5; claim is `mailto:<your address>` |
| `WEB_CONCURRENCY` / `CELERY_CONCURRENCY` | `2` / `1` (set by the Blueprint) |

### Vercel: project `sora` (root directory `frontend`)
| Variable | Value |
|---|---|
| `BACKEND_INTERNAL_URL` | `https://sora-api.onrender.com` (your Render URL; read at **build** time, redeploy after changing it) |
| `NEXT_PUBLIC_API_URL` | `/api/v1/auth` |
| `NEXT_PUBLIC_BACKEND_API_URL` | `/api/v1` |
| `NEXT_PUBLIC_GOOGLE_CLIENT_ID` | same as `GOOGLE_CLIENT_ID` |
| `NEXT_PUBLIC_VAPID_PUBLIC_KEY` | same as `VAPID_PUBLIC_KEY` |

`NEXT_PUBLIC_*` values are compiled into the browser bundle, so they must never hold secrets.

## 2. Step-by-step checklist

1. **Brevo:** create a free account, verify a sender (Senders, Domains & Dedicated IPs → Senders → add
   your address and click the confirmation email), then create an API key.
2. **Push the deploy branch** to GitHub (Render deploys from git).
3. **Render:** Dashboard → New → Blueprint → connect the GitHub repo → choose the deploy branch. Render
   reads `render.yaml` and asks for every `sync: false` value (§1). For `FRONTEND_URL` use the Vercel
   domain you expect (e.g. `https://sora-study.vercel.app`) and correct it after step 4 if needed. Use
   `NUM_PROXIES=1` for now.
4. **Vercel:** from `frontend/`: `npx vercel link`, add the env vars (§1) for Production, then
   `npx vercel --prod`. Note the production domain.
5. **Render:** set `FRONTEND_URL` to the real Vercel domain if it differs (the service restarts).
6. **Google sign-in (manual):** Google Cloud Console → APIs & Services → Credentials → the OAuth web
   client → *Authorized JavaScript origins* → add `https://<Vercel domain>`.
7. **Measure `NUM_PROXIES`** (§4) and update it on Render.
8. Run the smoke test (§3).

Migrations and `collectstatic` run on every start of the API container (`deploy/start.sh`).

## 3. Smoke test (after every deploy)

- [ ] Wake the API: open `https://<vercel domain>/api/v1/tasks/` and wait for the `401` JSON error envelope
      (proxy works, `DEBUG` off).
- [ ] `https://<vercel domain>/` loads over HTTPS.
- [ ] Sign up with a real address, receive the verification email, click the link, log in.
- [ ] Reload the dashboard: you stay logged in (refresh cookie works through the proxy).
- [ ] Upload a PDF and see its summary appear (worker running).
- [ ] Create a deck with 4 cards, take a quiz and see the score.
- [ ] Open the URL on a phone and install it to the Home Screen; it opens full-screen.
- [ ] Turn on airplane mode and open the installed app: the app shell or offline page opens.
- [ ] Enable notifications in Settings and receive a push (iOS: only from the installed app).
- [ ] `NUM_PROXIES` (§4): log in from two networks (Wi-Fi and mobile data) and confirm they are not
      throttled together.

## 4. `NUM_PROXIES` (SEC-03)

DRF identifies a client for throttling by the `X-Forwarded-For` entry that is `NUM_PROXIES` from the right.
Too high lets a client spoof its IP by sending its own header; too low puts users in a shared bucket.

Here two platforms sit in front of Django (Vercel's rewrite proxy, then Render's edge), so measure it.
The API's access log prints every request's `X-Forwarded-For` as `xff="…"`:
1. From your phone on mobile data, open `https://<vercel domain>/api/v1/tasks/`.
2. In Render → `sora-api` → Logs, find that request's `xff="a, b, …"` line.
3. Find your phone's public IP (search "what is my IP" on the phone). `NUM_PROXIES` = the number of
   addresses from your IP to the right end of the list, counting your IP. Example: `xff="198.51.100.7,
   76.76.21.9"` with your IP `198.51.100.7` → `NUM_PROXIES=2`.
4. Set it on Render and record the value here.

Measured locally on 2026-10-26: a self-hosted Next.js rewrite passes `X-Forwarded-For` through without
appending. Vercel's edge and Render's edge may each append, so the expected value is `1` or `2`. Record the
measured value here once deployed.

## 5. Web Push (VAPID) keys

```bash
npx web-push generate-vapid-keys
```
- **Public key** → `VAPID_PUBLIC_KEY` (Render) and `NEXT_PUBLIC_VAPID_PUBLIC_KEY` (Vercel).
- **Private key** → `VAPID_PRIVATE_KEY` (Render only; secret, never in the frontend or git).
- Generate a separate pair for production; don't reuse the development keys.

On iOS 16.4+ web push only works once the app is installed to the Home Screen. SORA tells iOS users to
install the app before enabling notifications.

## 6. `config.settings.demo` (laptop + tunnel fallback)

If the hosted demo is unavailable, run the stack on a laptop behind a TLS-terminating tunnel with
`DJANGO_SETTINGS_MODULE=config.settings.demo`. It is `prod` with two optional flags only:
`DEMO_SSL_REDIRECT=0` (the tunnel already did TLS) and `DEMO_CONSOLE_EMAIL=1` (print emails to the log).
`DEBUG` stays `False`, `ALLOWED_HOSTS` and CORS stay closed, and accounts must still verify their email.
`config.settings.dev` is **never** exposed publicly.

## 7. Local development

```bash
docker compose up -d db redis
cd backend && source .venv/bin/activate
python manage.py migrate && python manage.py runserver      # :8000
celery -A config worker -l info                              # second terminal
celery -A config beat -l info                                # third terminal
cd frontend && npm run dev                                   # :3000, proxies /api/v1 to :8000
```
The frontend uses the same relative `/api/v1` URLs locally; `BACKEND_INTERNAL_URL` defaults to
`http://localhost:8000`. Service workers are disabled in `next dev`; to test install/offline locally run
`npm run build && npm start`.

To boot the production image locally: `docker build -t sora-api:local backend` and run it with
`DJANGO_SETTINGS_MODULE=config.settings.demo DEMO_SSL_REDIRECT=0 DEMO_CONSOLE_EMAIL=1` plus a reachable
`DATABASE_URL` / `REDIS_URL`.
